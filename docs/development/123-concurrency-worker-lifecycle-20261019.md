# 并发预检中的后台进程与冷启动修复

冻结资料后的首轮回环预检没有通过，失败产物保留于`artifacts/local-concurrency/20261019T151053287454Z/`。真实长书已保存10页后终止并重启活动worker，但测试中的中断研究状态未恢复。对照试验仅给重启worker指定空输入后，同一检查点成功恢复为interrupted；说明继承控制管道会影响Windows后台启动。该研究状态是明确的合成故障输入，不是实际付费请求。

后台worker启动及模型配置重载统一使用`stdin=DEVNULL`。标准服务退出及重载通过`stop_worker`停止当前服务实际拥有的进程树，避免只结束Windows虚拟环境启动器后仍由实际Python子进程持有旧工作区锁。目标来自已有Popen句柄，不按全局Python进程名清理。不会修改环境中的真实密钥或自动重放未知付费结果。

随后预检在首次并发语义查询时超时，浏览器登录也被拖住。`20261019T151546332348Z/server-stderr.log`保存的线程栈显示：NumPy原生扩展正在首次导入，其他检索线程等待导入锁，ASGI线程同时等待创建线程。现将已声明为核心依赖的NumPy初始化放在API模块加载阶段，在处理并发请求之前完成；没有升级NumPy、ONNX或安装依赖，也没有禁用实际向量检索规避此问题。

12项worker生命周期、模型重配置边界和初始化并发回归通过，产物`artifacts/worker-process-20261019.xml`。扩大到阅读检索与冻结资料后，31项通过，`artifacts/concurrency-lifecycle-core-20261019.xml`。包括真实子进程启动、退出后进程存活检查、重新取得工作区锁，以及已退出worker的无害关闭。完整持续验收仍须另行执行，当前专项不能替代30分钟/15分钟负载结论。

预检工具自身也作了纠正：Windows已退出但仍有句柄的进程可能保留非零RSS，存活判断改用退出码；模型未配置的预期拒绝响应应为503；同一账号的不同文档分别核对解析运行清单，不能把共同PDF的解析ID误算为私有PDF缺失。上述预检失败均保留，不计为通过。

源码和测试原位修改；本记录为新增，原冻结PDF/CSV/清单及用户主库不变。后续持续验收固定源码指纹，保存接口时间分布、实际浏览器并行区间、任务与历史来源核对、内存观察及正常退出证据。
